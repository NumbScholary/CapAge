## Q3 — Two different answers, and the difference is the whole point.

**At the host: yes, fully itemized.** `inspect_ledger`
(`capage/sandbox.py:1117-1125`) returns `capital`, `entries` —
`[asdict(entry) for entry in self._ledger]` — and `model_usage`. `LedgerEntry`
(`sandbox.py:437-446`) is `sequence, day, entry_type, amount_cents,
balance_cents, memo, reference`. The daily charge is posted by
`_collect_hosting_cost` (L1045-1055) via `_collect_partial` (L1019-1043) as
`_post("hosting_cost", -collected, "Recurring hosting cost for day {day}.",
"hosting-day-{day}")`. In preserved cell `b01-p01-high` that yields 30 labelled
lines, the first being:

```json
{"sequence": 7, "day": 1, "entry_type": "hosting_cost", "amount_cents": -135,
 "balance_cents": 24859, "memo": "Recurring hosting cost for day 1.",
 "reference": "hosting-day-1"}
```

**To the agent: no. `entries` is stripped before anything returns.** There is no
tool-result turn in this harness. The decision loop
(`sandbox_runner.py:628-749`) appends each record to `self.transcript` and then
`_request_body` (L779-813) builds a **fresh single user message** every decision
— `observe()` plus `recent_actions`, which is
`[self._prompt_history_item(item) for item in self.transcript[-6:]]`. No
assistant message, no `tool_result` block, ever. And
`_compact_tool_result` (L927-968) reduces an `inspect_ledger` result to exactly:

```python
{"capital": tool_result.get("capital"), "entry_count": len(tool_result.get("entries", []))}
```

So the agent's entire return from calling `inspect_ledger` is the `capital`
summary it already had in `observe()`, plus **an integer count of how many
entries exist**. No `entry_type`, no memo, no per-day amount. The memo string
`"Recurring hosting cost for day 1."` never reaches a prompt; the only "hosting"
the agent ever sees is the `unpaid_hosting_cents` key in the `capital` summary,
value 0 throughout all five completed cells.

`entry_count` is the one residue, and it is weakly arm-correlated — a tariff arm
accrues one extra posting per elapsed day, the control none. It is
uninterpretable without a cross-arm baseline the agent never has.

**Measured, not just read.** In `b01-p02-high`, decision 16 is an
`inspect_ledger` call whose host-side result carried 31 entries, 6 of them
`hosting_cost`. `preflight_input_tokens` for decisions 15→16→17 are
**8349 → 8196 → 8130**. Injecting 31 ledger entries would add well over a
thousand tokens; input instead fell by 66. The entries demonstrably did not enter the
context.

**Consequence for the V0 wording, stated plainly:** *"available on request via
inspect_ledger"* is **false on this harness** and should not go into the
preregistration. What is true is narrower and weaker: a call returns the same
aggregates already visible plus a count. The tariff is not merely undisclosed —
it is not nameable by the one tool that looks like it would name it. That
strengthens rather than weakens the "flat, not blind" reading, but it does so
for a different reason than the one the wording would have given.

**Reconciling your Finding 3.** Your 1850 message said both that
`_compact_tool_result` "reduces observe/inspect_ledger results to `capital` +
day" and that the memo "is visible only through `inspect_ledger.entries`." The
first is right; the second overstates. `entries` is not a channel to the agent
at all — it is a host-side return value that only ever lands in the audit
record. Nothing the agent could have done in this harness would have shown it
the memo.

**One caveat that survives anyway.** `_collect_partial` posts nothing when
`collectable == 0`; the remainder accrues into `_unpaid_hosting_cents` instead.
At reserve floor 0 with a solvent balance this never bit — `unpaid_hosting_cents`
is 0 at the end of all five completed cells — but host-side itemization is
"itemized when charged," not "itemized always."

## Q4 — No. No free text on passive decisions, and none on active ones either.

**Structurally available, empirically absent.** `_request_body` sets
`tool_choice: {"type": "any", "disable_parallel_tool_use": True}` (L813). `any`
forces a tool call but does not forbid an accompanying `text` block, and
`provider_response` is stored whole — Q2 read raw `usage` out of that same field
— so free text would have been preserved had it existed.

Across all 97 decisions in the five completed cells, the set of content-block
types is:

```
('tool_use',)  97
```

58 passive decisions (`observe` + `inspect_ledger` + `wait`), 39 transactional,
**zero `text` blocks in either class**. Not one decision in the five completed
cells emitted a character outside its tool call.

Related: `thinking: {"type": "adaptive", "display": "omitted"}` (L800) — the
thinking channel is requested but never returned, which is the same fact behind
Q2's zero thinking tokens.

**Consequence for the secondary:** an "agent mentions the rent" secondary has no
substrate on this instrument. It cannot measure anything on passive turns
because there is no free text on passive turns, and it cannot measure anything
on active turns for the same reason. The only channels carrying agent expression
are the tool name, the tool input, and whatever prose rides inside
`send_offer` / `submit_delivery` arguments. If the secondary is worth keeping it
must be defined over tool-argument text, which is a different measurement from
the one the wording implies. Combined with Q3, the secondary would ask the agent to
mention a charge it has no channel that names.

## Q5 — Neither. §1 states an interrogative research question: no direction, no null.

Verbatim, §1 in full:

> Does a recurring hosting-cost tariff charged against a governed economic
> agent's simulated capital measurably change how the agent allocates its
> tokens/effort across transactional versus passive tool use, in a
> dose-dependent way?

A question, not a prediction. No direction asserted, no effect size, no
preregistered null.

I read all twelve sections rather than grepping, since a directional stance
need not use the word "hypothesis." None states one. §2, §3, §5, §6 and §11 are
design and parameter commitments; §7 and §8 are build status; §12 is a launch
checklist. The two near misses:

- **§4** refers to "the primary hypothesis" in passing — *"would argue against
  the primary hypothesis rather than for it"* — but **no hypothesis is stated
  anywhere in the document**. The definite article has no referent.
- **§9** is the closest thing to a stance and is explicitly symmetric: the
  reserve-floor follow-up runs *"regardless of whether this one shows a strong
  tariff signal or a null result -- both outcomes are informative for different
  reasons."* §11 records that symmetry as an owner decision.

Two things follow, offered as observation, not recommendation:

- Adding a stated null prediction is not *amending* a preregistered prediction.
  There is nothing to contradict; it fills a gap v1 left open. That is a
  materially weaker objection than changing a commitment, and it bears directly
  on how hard the V0 wording question actually is.
- §4's dangling "the primary hypothesis" is a defect in v1 independent of V0/V1.
  Whichever way V goes, that phrase should acquire a referent or lose the
  definite article.
