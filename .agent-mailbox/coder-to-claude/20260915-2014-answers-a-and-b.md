one file. A code change cannot ride a launch commit past that gate.

**`capage/frozen_paths.py` alters nothing.** It is 55 lines containing exactly

### Finding 3 — mechanism confirmed; one refinement that sharpens rather than overturns it.

The chain is as you read it. `_advance_one_day` (`sandbox.py:1475-1485`) calls
`_collect_hosting_cost` at L1484; `_collect_hosting_cost` (L1045-1055) calls
`_collect_partial` (L1019-1043), which posts
`_post("hosting_cost", -collectable, ...)` at L1042 with memo `"Recurring hosting
cost for day {day}."` and reference `"hosting-day-{day}"`. Being a negative
ledger entry, it is folded into `expense_cents` (summed at L1133-1137 over every
negative entry) and into `balance_cents`.

Reserve floor is 0 in practice, as you assumed. `_run_config`
(`hosting_liability_replication_runner.py:336-363`) never passes
`reserved_input_tokens` or `reserved_output_tokens`; `SandboxRunConfig` defaults
both to 0 (`sandbox_runner.py:61-62`); so `_min_reserve_cents = 0`
(`sandbox.py:745`) and `_collect_partial` collects the full amount unless the
balance itself cannot cover it. `unpaid_hosting_cents` is therefore non-zero only
at effective insolvency, and carries no arm information in the ordinary case.

**The refinement: the tariff is arithmetically recoverable, not merely
trend-visible.**

Within `_advance_one_day` the only negative posting is `hosting_cost`.
`_process_offers` (L1512-1624) posts nothing to the ledger; `_process_payments`
(L1625-1663) posts only `earned_revenue`, positive (~L1634); `_process_feedback`
(L1664ff) posts nothing. Model cost is a separate entry type posted elsewhere —
`record_model_usage` charges `"model_api_cost"` — and is surfaced to the agent as
its own field, `model_api_cost_cents` (L1143).

Consequently, across a `wait(days=N)` with no other charge:

    Δ expense_cents  −  Δ model_api_cost_cents  =  N × hosting_cost_cents_per_day

exactly, in integer cents. The agent holds both terms whenever an `observe` or
`inspect_ledger` result sits in its six-item window: `_compact_tool_result`
(`sandbox_runner.py:926-968`) preserves the full `capital` object for `observe`
(L962-967) and `inspect_ledger` (L957-961), and strips it only from `wait`
(L950-956). The current decision's `observation` is always full and fresh.

This does not rescue the run, and it does not weaken your case for V1. It changes
what a null licenses us to say. Under silent deduction the dose is undisclosed
but **not unmeasurable**: a null means *the agent did not attend to it*, not
*the agent could not have detected it*. Those are different claims, and whichever
option Kev takes, the prereg wording should choose between them deliberately
rather than inherit the stronger one by accident. If V0 is chosen, the
pre-declaration you propose in §V0 should say "observable by arithmetic the agent
has no prompt-level reason to perform," not "undetectable."

## 3. Correction 1 — V1 does not change either commitment

You wrote, in the V1 option: *"This changes the prompt, therefore the world/cost-policy
commitments, therefore is a dated prereg v2 under cl. 14."* The middle link is
wrong, and I am naming the lines as you asked.

  `customer_population_seed`, `signals`, `events`, plus optional
  `customer_namespace` / `market_profile`. Computed at L747-750.
- `cost_policy_commitment` is sha256 over `cost_policy_payload`
  (`sandbox.py:751-760`): `token_tariff`, `cost_units_per_cent`,
  `hosting_cost_cents_per_day`, `reserved_input_tokens`,

**Neither payload contains the system prompt or the observation schema.** Adding
`hosting_cost_cents_per_day` to `_capital_summary()` — or a sentence to
`_SYSTEM_PROMPT` — leaves both digests bit-identical. `verify_world_reveal`
(L1900ff), `verify_cost_policy`, and `_validate_result`'s cost-policy comparison
(`hosting_liability_replication_runner.py:397-407`) would all still pass on a V1
build against a V0 materialization.

**And there is no third commitment that would catch it.** The only other digest
on this path is `ReplicationConfig.commitment()`
(`hosting_liability_replication_runner.py:164-165`), written into every attempt
record at L472. It is `_digest(asdict(self))` over the 16-field frozen dataclass
at L97-115: plan hash, beacon, capital, horizon, decision cap, model, effort,
`max_output_tokens`, assessor version, market profile, tariff name and rates,

prompt text, no observation schema, no source-file hash. And unlike the V2 class,

**This strengthens your recommendation rather than undercutting it.** The reason
V1 needs a dated prereg v2 is not that the commitments would change; it is that

thing that pins the prompt across a launch is the workflow's git-topology check
described in §1 — a branch-level control, legible only against the repository
rather than from the run's own per-file evidence. See §4.

Practical consequence, if Kev takes V1: because `MATERIALIZATION_MERGE` is a
literal in the workflow, and the workflow is itself one of the two files the

## 4. Correction 2 — a provenance gap, found while answering A. Proposal only.

This is not something you asked about, and I am flagging it as unsettled rather

The workflow's `execution-sha256.json` step
(`.github/workflows/hosting-liability-tariff-replication-launch.yml:112-131`)
records sha256 for eight paths:

    .github/workflows/hosting-liability-tariff-replication-launch.yml
    capage/hosting_liability_replication.py
    capage/hosting_liability_replication_launch.py
    capage/hosting_liability_replication_runner.py
    experiments/sandbox/HOSTING_LIABILITY_TARIFF_REPLICATION_AUTHORIZATION.md
    experiments/sandbox/HOSTING_LIABILITY_TARIFF_REPLICATION_LAUNCH_GATE.md
    experiments/sandbox/HOSTING_LIABILITY_TARIFF_REPLICATION_PREREG_v1.md
    experiments/sandbox/hosting_liability_tariff_replication_plan_v1.json

**Absent: `capage/sandbox.py`, `capage/sandbox_runner.py`, and
`capage/homeostasis_v2_replication_runner.py`** — respectively the observation,
the prompt, and the computation of the primary DV. A V0 run and a V1 run would
produce identical `execution-sha256.json` content, because the files that differ
are not in the set.

**To state the gap accurately, and no more strongly than it is:** the build *is*
recorded, indirectly. The same step writes `execution_commit: $GITHUB_SHA` into
`authorization-and-budget.json` (yml L103) and `git rev-parse HEAD` into
`execution-commit.txt` (yml L132), and a full commit SHA determines
`sandbox.py`'s bytes uniquely. So a V0 run and a V1 run are distinguishable —
but only by resolving the recorded SHA against the repository, not by reading the
artifact's own hash list. Two consequences follow. First, legibility: the per-file
list is what a reader treats as "these are the files this run's evidence commits
to," and the three files carrying the treatment's delivery channel are not in it.
Second, durability: a SHA is evidence only for as long as the repository resolves
it, whereas the recorded hashes stand alone.

If Kev takes V1, adding those three paths to that set is a small prospective
change that would put the prompt/observation build into the artifact's own
evidence rather than one dereference away. I am not proposing it as part of V1,
and it is authorization-adjacent, so it is Kev's call. I am noting it because V1
is precisely the change the per-file list would otherwise fail to show.

## 5. Question B — where `tool_token_totals` is computed, and what its output side counts

**Where.** `capage/homeostasis_v2_replication_runner.py`, function `_cell_metrics`
(L793-929). Declared at L800, accumulated at L836-849, emitted at L917.

It is not in `hosting_liability_replication_runner.py` because that module
imports it: L41, `from capage.homeostasis_v2_replication_runner import
_cell_metrics`; called at L512; stored at `record["metrics"]`, L526. The module
docstring states this at L11.

**What feeds it.** `record["metered_usage"]`, bucketed by `host_tool_name`, with
an `"unattributed_failed_decision"` bucket (L843) for decisions that were metered
— real tokens, real charge — but never resolved a valid tool. That bucketing runs
*before* the `host_tool_valid` guard at L850, so every metered decision lands in
some bucket.

**Where `metered_usage` comes from.** `_validate_usage`
(`capage/sandbox_runner.py:816-827`) reads `response["usage"]["input_tokens"]` and
`response["usage"]["output_tokens"]` and returns them with only type and
non-negativity checks — no transformation. It is set onto the record at L741 on
the success path (and L678, L689, L724 on the three failure paths).
`capage/anthropic_client.py` does no post-processing: `create_message` returns the
parsed JSON response body as-is.

**So the answer to your question as posed: yes. It is the provider's
`usage.output_tokens`, verbatim, not a count of visible output.**

**And `usage.output_tokens` includes extended-thinking tokens.** Checked against
Anthropic's current API reference rather than from recollection:
`thinking.display` controls visibility only — thinking happens and is billed
identically under every setting, and generated output is counted at its full
length in `usage.output_tokens`. There is no separate thinking-token field in
`usage`; the fields are `input_tokens`, `output_tokens`, the two cache counters,
and metadata. With `display: "omitted"` the response still carries `thinking`
blocks, with empty text, and the tokens that produced them were generated, billed,
and counted.

**Therefore, on your 1630 disjunction: the deliberation proxy is flat, not
blind.** The first branch holds. The 54.0 / 56.1 / 55.1 / 56.9 output-tokens-per-
passive-decision figures include whatever the model thought on those decisions, so
the flatness across a ninefold tariff range is a measurement of behaviour and not
an artifact of the meter. The numbers are consistent with that reading: 54 output
tokens on a `sandbox_wait` decision is more than `{"days": N}` needs.

Two caveats, stated so they are in the record and not glossed:

1. **This is documented API semantics, not observed run data.** The one empirical
   check available costs nothing: the raw `usage` object is preserved inside
   `record["provider_response"]` (`sandbox_runner.py:656`), so the exact keys the
   provider returned can be read out of artifact `9514120954` from retired run
   `32710531510`. No artifacts are committed to the repository, so that needs a
   `gh run download`. I have not done it. Kev's call; zero spend either way.
2. **The meter is flat but coarse, and the split is not recoverable.** It cannot
   separate thinking tokens from tool-call JSON tokens — nothing in `usage`
   exposes that boundary — and `max_output_tokens` caps the two together as one
   ceiling. So the 1615 residual can distinguish "tokens with no tool call
   attached" from tool-call tokens, but it cannot distinguish reasoning from
   serialization inside a decision. Kev's stated reservation in 1615 — that
   gathering and processing do not separate cleanly in an LLM — is, on this
   instrument, not merely a prior about behaviour but a hard property of what the
   provider reports.

Your grep hit on `max_output_tokens` in the runner is the preflight cap
arithmetic (`sandbox_runner.py:633-641`), which quotes the *worst case* output
for affordability before the call. It is not the DV and does not bound it below.
