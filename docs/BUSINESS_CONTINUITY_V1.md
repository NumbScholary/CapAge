# CapAge Business Continuity v1

Business continuity is authoritative host state, not model memory. Each
experimental arm owns a separate JSON-safe ledger with stable customer IDs,
interaction counts, hidden bounded reputation points, and the latest observable
outcome. A frozen customer-population seed determines each recurring customer's
core budget, responsiveness, payment reliability, and quality threshold. Month
seeds may change demand, intent, availability, and public events without
silently replacing the customer's underlying personality.

The state changes only when the synthetic environment records an actual offer,
acceptance, independent delivery assessment, settlement, dispute, or feedback
response. Good assessed work can improve later acceptance odds; poor work can
damage them. A prior customer also receives a small search-discovery advantage,
simulating the lower cost of maintaining an existing relationship.

Every accepted contract includes a committed customer task brief. The brief
contains three source records and a disclosed scoring formula. Assessor v2
requires a strict JSON delivery with calculations for all records, the correct
recommendation, a customer explanation, and concrete implementation steps.
The host selects the task type from the market need; the model's proposed scope
and tags cannot change the scoring rubric.

Model observations expose customer identity and factual prior outcomes. They do
not expose the numeric reputation score or unrequested satisfaction. The model
cannot create customers, edit continuity, assess a delivery, or settle payment.

Both longitudinal arms use the same mechanism but maintain isolated ledgers.
Consequently, any endogenous divergence in repeat business follows each arm's
own actions and outcomes rather than cross-arm contamination.

The schema deliberately excludes unresolved contracts. The runner stops at an
open obligation until active-contract serialization is separately designed and
tested.
